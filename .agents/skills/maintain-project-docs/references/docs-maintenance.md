# docs 维护流程

## 1. 确定本次影响

- 先读用户目标和实际改动，按模块、公开符号、命令、配置键、文件路径搜索文档。
- 同时看根 README、相关模块 README、docs 和活跃 notes；不要只搜索文件名，也搜索旧参数名、旧路径和行为描述。
- 有明确变更时只处理相关页面；用户明确要求文档审计时才扩大扫描，并先报告发现，不未经授权重组整棵文档树。
- 找不到 docs 时按 [目录规范](docs-structure.md) 建立最小入口及当前需要的页面，不先搭满目录。

## 2. 建立事实依据

| 文档信息 | 优先核对对象 |
|---|---|
| 安装、运行、测试命令 | 项目版本约束、真实脚本、CLI help、安全环境中的运行结果 |
| 配置、默认值、优先级 | 配置 schema、解析/合并实现、示例、覆盖测试 |
| API、事件、错误、兼容性 | 公开类型、接口实现、协议定义、契约测试 |
| 架构、生命周期、所有权 | 入口、模块依赖、调用路径、状态处理实现、活跃决定 |
| 部署、迁移、回滚 | 实际构建部署配置、产物、权限前提、获授权的验证记录 |

不能从 README 推导出未经核实的源码行为，也不能把测试文件的存在当作测试通过。既有文档与代码冲突时，先判断是不是实现违反约定；未解决的冲突明确说明，不擅自修改业务代码或把异常行为写成承诺。

## 3. 就地同步

- 优先修改拥有该事实的页面，只把必要摘要和链接放到入口。
- 参数变化同时核对参数表、命令示例、环境变量、默认配置及失败说明，避免只改一处文字。
- 文档说明已实现行为、前置条件与限制；未实施方案进入 proposed，不混入上手教程。
- 删除失效的重复说明前确认其独特信息和入站链接；批量删除、迁移或覆盖重要内容需要明确授权。
- 生成页面修改源定义后通过已有命令再生成；不能运行生成器时报告缺口，不手改生成物伪装成功。
- Monorepo 按 [分层规范](monorepo.md) 检查提供方、消费方与根级集成内容，不复制共享事实。

## 4. 与 notes 联动

先独立判断 docs 是否受影响，再判断是否值得记录决定。决定已记录且理由未变，只同步原 Note 的事实；有新的长期约束或取舍才新建。状态流转时同步相关 docs 链接，不让现状文档继续把提案当作实现依据。

## 5. 验收与汇报

- 受影响页面从入口可达，相对链接与文件名大小写匹配；图片、源码路径和跨包链接存在。
- 已移除失效参数、旧路径和错误默认值；有效的旧版本兼容说明不能误删。
- 命令注明工作目录、环境和必要前提；涉及部署、生产数据、费用或权限时，不为验证文档擅自执行。
- 优先运行已有文档构建与链接检查；没有工具时人工核对本次涉及的路径、标题锚点、命令和事实，明确验证边界。
- docs 与 implemented 一致；proposed、rejected、archived 不被当成当前能力来源。
- 汇报改动对象、事实来源、实际执行的检查和剩余缺口；没运行不写“已验证”。

## 场景验收样例

| 输入场景 | 应有行为 | 不应发生 |
|---|---|---|
| 配置键机械改名 | 更新配置表、示例和已有 Note 引用 | 因“机械改动”漏掉 docs，或强制新增 Note |
| 讨论尚未实现的缓存方案 | 有记录价值时写 proposed | 在现状文档宣称缓存已生效 |
| 包 A 改接口，应用 B 消费 | 更新 A 接口说明、B 示例、受影响的集成文档 | 只看 A 的修改文件，或复制 A 的整份接口文档 |
| 已有集中式 docs 和 ADR | 沿用目录与格式，补实际缺口 | 强制迁移，或对非原生 ADR 使用原生校验器 |
| 单页即可讲清的小工具 | 最小文档入口及必要说明 | 为满足结构生成空 architecture/operations 页面 |

这些是人工行为验收标准，不是自动化测试已覆盖的声明。
